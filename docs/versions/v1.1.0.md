# v1.1.0 · 扫描性能与执行反馈

状态：本地专项验收完成，最终候选完整回归由直接推送后的 CI 矩阵承担；未发布。对应 G2-04—06。前置：[v1.0.1](v1.0.1.md)。遵守[开发约定](development-rules.md)。

## 1. 目标与范围

减少逐请求建连和重复统计开销，让配置的有界 HTTP 并发真正生效，并用局部更新替换任务页整页刷新。先测再改；不整体迁移 asyncio、不引入消息队列，也不在本版重写发现策略或启动桌面开发。

## 2. 分片实施

### A · G2-04 网络生命周期

- 将 HTTP Client 从单次请求提升到任务内可复用生命周期，按身份和实际代理配置隔离；任务结束或取消时关闭。
- 保持逐请求目标检查、显式重定向和 admission 回调。匿名模式不得因 Client 自动保存 Cookie 而改变既有请求身份语义；连接复用不等于改变 Cookie 策略。
- 同一任务切换代理/身份时使用对应实例，不创建全局可变客户端池。
- 用真实 keep-alive 本机站点比较连接数与耗时；不把 MockTransport 结果当 TCP 复用证据。

### B · G2-05 热点与有界执行

- 给请求、解析、入队、证据提交、快照更新计时；复用现有 timing/metrics，不增设监控平台。
- 只优化基准中的热点：候选批量入队、统计快照降频、必要查询索引。关键发送/观察事务保持恢复语义；终态强制刷新统计。
- 在持久 HTTP 执行器落实已有 origin_concurrency，默认 1，上限 4；使用有界 worker，各 worker 不共享 ORM Session，不跨网络等待持有数据库写事务。
- 暂停阻止新增发送；实际请求、重试及重定向仍经过同一 admission/预算控制。没有持久选项的旧调用保持现有串行含义。

### C · G2-06 实时反馈

- 新增 GET /api/scans/{id}/events SSE，只传当前任务的脱敏状态投影；不创建持久事件表，不建立事件溯源系统。
- 连接建立时发送完整快照，变化后合并发送；前端重连重新获取快照。使用原状态 API 作为唯一低频轮询回退，不叠加多套重连机制。
- Web 更新阶段、计数、等待原因和已用时间，不刷新整页；CLI 复用同一摘要。数据未变化时显示耗时与等待，不假造进度。
- 保留已有状态 API；旧记录缺失字段仍为未知。只对新建任务提供新增实时信息。

## 3. 接口与实现位置

优先改 [HTTP 网络层](../../app/services/scan_network.py)、[持久 HTTP 执行](../../app/services/collection_http.py)和[扫描路由](../../app/api/routes/scans.py)。事务、admission、任务模型和模板沿现有模块扩展。不为 Client 建供应商框架，不新增状态模型替代已有执行阶段。

### G2-04：网络生命周期

- HttpScanGateway 提供任务作用域，按上下文和实际代理选择复用 Client；每次发送仍先目标检查、显式跳转、admission。共享的只是任务内 HTTP 连接池，不共享 ORM Session。无任务作用域的独立 fetch 使用短生命周期并立即关闭。
- 匿名 CookieJar 拒绝响应 Cookie，保持逐请求匿名语义。固定三上下文中的匿名 HTTP 收集也有独立作用域；登录/独立身份使用原有认证或浏览器边界，不混入匿名连接状态。结束、异常、取消均执行 finally 关闭。
- 真实 HTTP/1.1 socket 测试先失败（task_scope 尚不存在），实现后通过：同任务 3 请求只建立 1 条连接，Cookie 始终未发送，正常和异常出口均确认 socket 关闭。不是用 MockTransport 证明 TCP 复用。

### G2-05：热点与有界并发

- 开发前 cProfile 20 页：collector 约 1.073 秒；check_lease 204 次约 0.212 秒，before_send 约 0.186 秒，persist 约 0.158 秒，enqueue 约 0.120 秒。500 页基线发出 500 次请求/建 500 条 TCP 连接，scan 44.9855 秒、CPU 42.8039 秒。
- 优化实际热点：统计快照至多每秒一次，终态/超时强制刷新；来源匹配改为同一次快照内按 URL+method 建索引，避免每个资产再扫描整个 ledger；新增证据查询用该任务的最大证据 ID 边界，避免重复搬运历史全部 ID。不建立全局缓存或通用批量入队框架，队列去重、scope 和限额仍经过原 enqueue 入口。
- 持久 HTTP 有界 worker 数 1—4；各 worker 在本线程创建/关闭自己的 Session，发送前及响应入账使用原 admission/事务，协调锁不跨网络或等待持有。发送、重定向、重试、跨队列源门禁及暂停仍按已有预算与租约验证。
- 新的“在途槽”仅用于 HTTP/redirect/sitemap；不在浏览器 route 回调或身份验证回调上等待自身事件循环。浏览器和身份继续使用原有调度边界。
- 并发小样本先复现设置 2/4 仍串行，修复后实际最大并发 1/2/4 与配置一致，均只有 7 次允许请求，requests/responses/observed 全部对账；暂停后不新增 admission，在途响应仍保存。
- 开发回归曾发现：预算拒绝后 worker 留着读事务等待协调锁，导致另一个 Session commit 被阻塞；已改为在等待清理锁前回滚该 worker 的读快照，没有新增重试、加长超时或吞掉数据库错误。
- 请求、解析、入队、证据提交与统计快照耗时记录在原 queue.telemetry.phase_seconds，旧队列为 null/未知，不伪造历史计时。

### 正式性能比较

命令（每种最终配置一次 500 页）：

```bash
PYTHONPATH=. python scripts/benchmark_collection_transport.py --transport http --rounds 1 --per-round 20
PYTHONPATH=. python scripts/benchmark_collection_transport.py --transport http --rounds 1 --per-round 500 --concurrency 1
PYTHONPATH=. python scripts/benchmark_collection_transport.py --transport http --rounds 1 --per-round 500 --concurrency 4
```

| 同机合成语料 | 扫描耗时 | TCP 连接 | 实际请求/已观察 | Python 最大 RSS | Python CPU |
| --- | ---: | ---: | --- | ---: | ---: |
| 基线 v1.0.1，500 页、间隔 0 | 44.9855s | 500 | 500 / 500 | 137461760 B | 42.8039s |
| 最终候选，并发 1 | 24.7466s | 1 | 500 / 500 | 130695168 B | 22.7301s |
| 最终候选，并发 4 | 24.5526s | 1 | 500 / 500 | 140148736 B | 23.6305s |

- 串行耗时下降 **44.99%**，并发 4 下降 **45.42%**，达到 25% 目标。RSS 串行约 -4.9%，并发 4 约 +2.0%，符合有界连接/线程开销；未引入后台池。
- 零延迟本机目标的瓶颈仍主要是 SQLite 短事务；提高并发不保证更快，因此默认保留 1。有延迟的真实 20 页小样本并发 4 使用 3 条 TCP 连接、所有 20 条观察对账；实际 overlap 另由有界发送测试核销。
- 中间候选曾测得 19.53s / 21.57s，不作为最终表格；最终测量与相关浏览器回归在共享开发机上有重叠，不能当成隔离压测或统计显著性结果。两次最终样本之间仅 CLI 等待原因展示发生修改，HTTP 执行文件未改变，两个源码摘要均如实保留。
- [结构化结果、环境与源码摘要](../benchmarks/v110-http.json)。全量本地日志、数据库和 profile 在隔离工作区 `.verification/`，未写入敏感数据。

### G2-06：局部实时反馈

- 新任务 options 保存反馈版本标记；旧记录无标记则不提供新增实时信息，原状态 API 保留，SSE 对旧任务给出明确冲突提示。
- `GET /api/scans/{id}/events` 建立时发完整 snapshot，变化后合并推送，断开连接退出；不创建事件表。投影仅有任务 ID、阶段、状态、实际计数、等待原因和时间，不发送目标 URL、原始异常、Cookie、报告路径等材料。
- 状态 API 的 execution_feedback 和 SSE 复用同一显示投影；CLI 使用相同活动计数字句并显示等待原因。未变化时只更新耗时和等待，不增加百分比。
- Web 使用单一 EventSource；断线后关闭该连接并以原状态 API 每 4 秒查询，不叠加另一套 SSE 重试循环。重新建立 SSE 连接始终收到当前完整快照，不假装从持久事件日志续读。
- 不替换整页 DOM，保持滚动和 details 展开/折叠；终态显示“查看最终报告与诊断”入口，用户打开后读取完整终态报告，不强制刷新页面。无新增依赖、迁移或状态模型。
